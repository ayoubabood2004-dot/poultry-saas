# عقد 0033 — الفاتورة الاحترافيّة (المرحلة ١ من `docs/SALES_PLAN.md`)

المرجع: DECISIONS 2026-11-17 «نظام المبيعات الاحترافيّ» (أجوبة المالك)، ومهارة `pos-sales-system` (القوانين 1–16، و`references/02-checkout.md` و`05-reliability.md`).
وكيلان بالتوازي (القاعدة والشاشات)، ثمّ الدمج يمرّر **أجوبة القاعدة الحقيقية** بمحلّلات الشاشات الحقيقية.

## المبادئ
- **الخادم يقرّر المال والمخزون:** المجاميع والخصم الموزَّع والكلفة (FIFO بالدفعات) والدين من الخادم بمعاملة واحدة؛ الجهاز يرسل ما قرّره الإنسان وحده (الموادّ والوحدات والكميات والأسعار والخصم والدفعات).
- **نداء واحد بمرجع `client_ref`، يُحفظ فوراً** (لا مسوّدات، DECISIONS:557)، والإعادة بالمرجع نفسه ترجع النتيجة الأولى. **لا تدخل الطابور بلا نت** (المهارة 13).
- **البيع على نقص يُرفض كما الآن** (`insufficient_stock` بتلميح يسمّي المادّة والمتاح)؛ المهارة تخالف هنا والمشروع يغلب (FOUNDATION 12–14).
- **لا حذف:** الفاتورة تُلغى كلّها بـ`void_sale` (بعد تعديله للسطور والسيقان)، والمرتجع والتصحيح في المرحلة ٢.
- **التوافق:** `record_sale` بتوقيعها ونتائجها تبقى تعمل (الواجهة المنشورة بين التطبيق والدمج)، وتُبنى على الجسم الجديد إن أمكن بلا تغيير سلوكها.

## أ. القاعدة — `supabase/migrations/0033_sales_invoice.sql` و`rollback_0033.sql`

### تغييرات الجداول (إضافة أعمدة، بلا كسر الصفوف القائمة)
- `sales_invoices`: `discount_total numeric not null default 0` (مجموع الخصم بالدينار)، `invoice_discount numeric not null default 0` (خصم الفاتورة كما كُتب)، `note text` (≤ 500 بلا فراغ في طرفيه)، `walk_in boolean not null default false`، `total numeric` (صافي الفاتورة، يُملأ للقائمة)، `paid numeric` (المدفوع الآن)؛ و`payment` يقبل `'mixed'`/`'partial'` أو يُستبدل بقاعدة: **الدين = الصافي − المدفوع ≥ 0**. قيد `sales_invoices_payment_check` يُعاد كتابته ليقبل القديم والجديد. والزبون النقديّ: `walk_in = true` يستلزم الدفع كاملاً.
- `sales_lines`: `unit_label text`, `unit_factor numeric` (إلى الأساس)، `unit_qty numeric` (الكمية بوحدة السطر)، `unit_price_unit numeric` (السعر لوحدة السطر، فلسان)، `gross_total numeric` (الكمية × السعر مقرَّباً لأقرب دينار)، `line_discount numeric` (خصم السطر بالدينار)، `invoice_discount_share numeric` (نصيبه من خصم الفاتورة بأكبر الباقي)؛ و`line_total = gross_total − line_discount − invoice_discount_share ≥ 0` بالدينار. `qty` (الأساس) و`unit_price` (للأساس، للعرض القديم) يبقيان مملوءين. والصفوف القديمة: الأعمدة الجديدة تُملأ بالتحويل (وحدة الأساس، معامل 1، بلا خصم).
- `sales_payments` (جديد): سيقان الدفع `(id, org_id, sale_id, leg_no, cash_account_id, amount, payment_entry_id, cash_move_id)`؛ RLS قراءة كـ`sales_invoices`، ولا منح كتابة؛ محفّز التدقيق؛ `classes.json` وكلّ تسجيل تطلبه الحزمة. الفاتورة القديمة النقدية تُنقل ساقاً واحدة (`leg_no = 1`) فيصير للمدفوع مصدر واحد.

### الزبون النقديّ
- `walk_in`: يُكتب على طرف نظاميّ واحد لكلّ منشأة «زبون نقديّ» (يُنشأ عند أوّل استعمال بعلامة نظاميّة، لا يُختار للدين ولا يظهر في قوائم الزبائن العادية، ورصيده صفر دائماً لأنّ كلّ فاتورته مدفوعة). أو بديل يحفظ صدق الدفاتر بلا طرف — قرار الوكيل بشرط: قيد الفاتورة والدفعات صادقان، و`money_overview`/`money_moves` يعدّان النقد بيعاً نقدياً كما الآن، والثوابت تمسك أيّ رصيد له.

### الكاتب `public.record_sale_v2`
```
record_sale_v2(p_client_ref uuid, p_sale_id uuid, p_warehouse uuid, p_party uuid /* null = زبون نقديّ */, p_sold_on date,
  p_lines jsonb, p_invoice_discount numeric, p_payments jsonb, p_note text) returns jsonb
```
- `p_lines`: `[{ "line_id": uuid, "item_id": uuid, "unit_id": uuid | null /* null = وحدة الأساس */, "qty": "2" /* بوحدة السطر، ثلاث مراتب */,
  "unit_price": "25000.00" /* لوحدة السطر */, "discount": "0" /* دينار */ }]` — 1..100 سطر، معرّفات فريدة، الوحدة من `item_units` للمادّة (`for_sale`، غير مؤرشفة).
- `p_payments`: `[{ "leg_id": uuid, "cash_account_id": uuid, "amount": "15000" /* دينار صحيح */ }]` — 0..5 سيقان، صناديق مختلفة غير مؤرشفة.
- الفحوص (بترتيب `record_sale` نفسه وقوانينه): `sale.record`، الفترة، المخزن في النطاق، الطرف زبون (أو null)، التاريخ (السبعة أيّام وقفل الفترة)، الموادّ قابلة للبيع (`not_sellable` للبيض والأفراخ في هذه المرحلة)، الأقفال بترتيب المعرّف (`lock_masters`/`lock_balances`)، المخزون لكلّ سطر بعد جمع سطور المادّة نفسها (`insufficient_stock` بالمتاح)، الخصم ≤ قيمة السطر وخصم الفاتورة ≤ مجموع السطور بعد خصومها (`bad_discount`)، المدفوع ≤ الصافي (`overpaid`)، والنقديّ يدفع كلّه (`walk_in_unpaid`)، والملاحظة.
- الكتابة: الفاتورة وسطورها (ترقيم من نوع المخزن كما الآن)، والسحب FIFO لكلّ سطر وكلفته في `sales_line_costs`، وقيد `invoice` بالصافي في دفتر قسم المخزن، ولكلّ ساق قيد `payment` وحركة صندوق `party_payment` **مخصَّصة لهذه الفاتورة**، والدين = الصافي − المدفوع.
- الإعادة: بالمرجع (`ref_claim`) وبمعرّف الفاتورة تحت قفل كما في `record_sale` (نفس المحتوى = النتيجة نفسها، غيره `id_conflict`).
- الجواب: `{ "sale_id", "doc_no", "sold_on", "total", "discount_total", "paid", "debt", "walk_in", "lines": [{ "line_id", "item_id", "qty_base", "line_total" }] }` (المال نصوص بالدينار؛ الكلفة لا تُرجع).

### القرّاء
- `sale_catalog(p_warehouse uuid)`: موادّ المخزن القابلة للبيع: `[{ item_id, name, barcode, kind, category, base_unit, available /* بالأساس، نصّ */, sell_price /* للأساس، أو null */, units: [{ unit_id, label, factor }] }]` بترتيب الاسم؛ يقرؤه كلّ من له `sale.record`.
- `sale_detail(p_sale_id)` يزيد: الوحدة والكمية بها وسعرها، والخصمان، و`payments` (الصندوق باسمه والمبلغ)، و`total`/`paid`/`debt`/`walk_in`/`note`/`posted_by_name`؛ والكلفة والربح لأدوار الكلفة وحدها كما الآن (`strip_cost`).
- `sales_overview` يزيد لكلّ فاتورة: عدد السطور، واسم المادّة الأولى، و`total`/`paid`/`debt`/`discount_total`، و`walk_in`، بلا افتراض سطر واحد.
- `sales_report`: يقرأ `line_total` الصافي (الخصم داخله) ويبقى بتجميعاته.
- `void_sale`: يعكس كلّ السطور والسيقان (والنقد المقبوض يبقى رصيداً للزبون كما الآن، والنقديّ يُردّ… **قرار الوكيل بشرط صدق الدفاتر**، يُكتب في رأس الهجرة).

### الثوابت والفحوص
- `verify_sales` لكلّ السطور: صافي السطر = الإجمالي − الخصمين ≥ 0، ومجموع أنصبة خصم الفاتورة = خصمها، ومجموع السطور = قيد الفاتورة = `total`، ومجموع السيقان = `paid` ≤ `total`، والنقديّ مدفوع كلّه ورصيد طرفه صفر؛ و`verify_money` يبقى صفراً.
- `supabase/tests/sales-invoice.test.mjs` (بادئة معرّفات وهواتف جديدة تُفحص على الملفّات كلّها): فاتورة بعدّة سطور ووحدات وخصمين وسيقان، والتوزيع بأكبر الباقي، والنقص، والزبون النقديّ، والإعادة، والإلغاء، و`record_sale` القديمة كما هي، والصلاحيات، والطفرات، والتراجع (يرفض بصوت ما دامت فاتورة بأكثر من سطر أو بخصم أو بأكثر من ساق). **عيّنات حقيقية** `SALES_SAMPLES_OUT=1` ← `scripts/tests/fixtures/sales-0033.json` (`sale_catalog`، و`record_sale_v2` بأنواعه، و`sale_detail` لفاتورة متعدّدة ونقدية وقديمة، و`sales_overview`).

## ب. الشاشات

### `/sales/new` — الفاتورة (حزمة المخزون الكسولة، خارج التثبيت المسبق)
- **المخزن** أوّلاً (واحد افتراضاً إن كان واحداً)، ثمّ **إضافة الموادّ**: بحث بالاسم وخانة باركود (الماسح يكتب كالكيبورد وEnter يضيف)، وبطاقات الموادّ بـ«المتاح».
- **السلّة:** لكلّ سطر الوحدة (قائمة وحدات البيع، والأساس)، والكمية، والسعر لوحدته (مقترح = سعر البيع × المعامل)، وخصم السطر، وصافيه؛ وحذف سطر. تحذير بالمتاح إن زادت الكمية.
- **الفاتورة:** خصم الفاتورة، والزبون (بحث، «زبون جديد»، أو «زبون نقديّ»)، و**الدفع:** «دفع الآن» بسيقان (صندوق + مبلغ، «أضف صندوقاً»)، و«الباقي دين» يُحسب حيّاً، و«ادفع الكلّ» بضغطة؛ والملاحظة والتاريخ.
- **المجموع** ثابت أسفل الشاشة: الإجمالي، والخصم، والصافي، والمدفوع، والدين. وزرّ واحد يسمّي النتيجة («احفظ الفاتورة — 3 موادّ، 125,000 دينار، منها 50,000 دين»).
- **قبل الحفظ:** قراءة أسعار البيع من جديد، وما تغيّر يُعرض ويُقرّ (المهارة 11).
- **الطلب المعلّق** (نتيجة مجهولة) يُحفظ خارج المكوّن (sessionStorage بمفتاح المستخدم والمنشأة، والذاكرة إن تعذّر) فالرجوع والعودة وإعادة التحميل تعيد الشاشة مجمَّدة به و«أعد المحاولة» ترسله حرفاً؛ والنافذة «فيها ما لم يُحفظ» ما دام في الطريق (درس 2026-11-10). **ويُصلَح مثله `SaleDialog` القائم** أو يُستبدل بالتحويل إلى `/sales/new?item=…&store=…`.
- `quietly`/التثبيت: لا صنف Tailwind جديد، ولا شيء في الإقلاع؛ والسقوف بلا رفع.

### صفحة الفاتورة `/sales/:id`
- تفاصيل كاملة (السطور بوحداتها وخصوماتها، والسيقان، والدين، والبائع، والملاحظة)، والربح لأدوار الكلفة.
- **«أرسل صورة»** (صورة أنيقة بعرض ثابت: الشعار واسم المنشأة، الرقم والتاريخ، الزبون، السطور، المجاميع، المبلغ كتابةً إن وُجد مساعده، «شكراً») تُفتح بها نافذة المشاركة (واتساب) أو تُنزَّل؛ و**«اطبع أو احفظ PDF»** بتخطيط A5. مساعد الصورة `html-to-image` **لا يدخل التثبيت المسبق** (حزمة مشتركة بين المخزون والقاعات تُستثنى بالاسم في `vite.config` و`pwa-guard`، أو نسخة محلية للمخزون — قرار الوكيل بشرط القياس).
- **«استلم من الزبون»** لدين الفاتورة (التحصيل القائم `record_party_payment` بدفتر الفاتورة، مخصَّصاً لها إن أمكن، وإلّا الأقدم أوّلاً كما الآن ويُقال ذلك).
- قائمة `/sales`: بطاقات/جدول بالصافي والمدفوع والدين و«نقديّ»، وعدد السطور.

### الفحوص
- `sales-invoice-screens.test.mjs` (DOM حقيقي): السلّة والوحدات والخصمان والسيقان والدين الحيّ، والزبون النقديّ، والباركود، والأسعار المتغيّرة، والطلب المعلّق بعد إعادة التحميل، والصورة والمشاركة، و«استلم»، والصلاحيات؛ و**دمج** يمرّر `sales-0033.json` الحقيقية بالمحلّلات الحقيقية.
